# Verified multi-commit Change Proposal publication

## Intent and success criteria

Developer Agents must be able to publish several commits, including resolved merges of the repository's default branch, without losing their Git ancestry. A publication succeeds only from a fully committed workspace. A published commit retains its exact object ID, parents, author, committer, message, and timestamps; Omnigrex remains the authority for credentials, branch selection, mutation fencing, and recovery. In particular, merging `main` in the workspace and publishing must make that merge an ancestor of the Change Proposal head, rather than merely copying its resulting files.

This change fixes the publisher for future Agent Turns and permits a new Developer Turn to repair the existing PR #16. It does not automatically merge Pull Requests, require that a moving default branch remain merged forever, or implement unfinished-workspace retention from issue #17. A successful publication is not a guarantee that GitHub will currently consider a PR mergeable.

## Existing boundary and failure

`internal/workspace/publish.go` currently creates a trusted checkout at the expected old head, copies only the workspace's file tree, makes one orchestrator-authored commit, and pushes it with a lease. The workspace's `.git` history is excluded. `internal/workspace/reconcile.go` looks for an operation trailer on that single-parent commit. Thus a locally committed merge of `main` can produce a published commit with only the old PR head as parent. Subsequent Agent Turns replace the workspace with a checkout of the published head, so they cannot rely on the discarded local merge commit.

## Publication contract

`publish_changes` requires a Git-clean workspace: no staged changes, unstaged changes, unresolved index entries, or non-ignored untracked files. Ignored local build artifacts are permitted and never published. The command's `message` argument becomes an optional audit summary stored with the mutation; it is not used to create or rewrite a Git commit. Old calls providing it remain valid. The Developer Agent Profile and the tool description must explicitly instruct agents to commit before publishing and explain actionable clean-workspace or history-validation errors.

For an existing Change Proposal, the proposed workspace `HEAD` must be a first-parent descendant of the exact expected remote head. For the first publication, it must similarly descend from the selected exact default-branch revision. Rewriting an already published commit, grafting unrelated history, or moving the branch to an arbitrary commit is rejected. Each outgoing merge commit may have one additional parent, which must be verifiably in the repository's default-branch history. Multiple such merges are allowed. A valid historical default-branch parent need not be the latest tip when publishing; a moved or rewritten default branch that makes the claimed parent unverifiable fails safely. Octopus merges, parents from other branches, unsupported tree entries, replace/graft/shallow history tricks, and malformed objects are rejected. Validation must use original Git objects in a trusted checkout, not merely agent-controlled refs or local Git configuration.

An orchestrator-controlled checkout imports only the proposed reachable commits, verifies the exact object ancestry and supported entries for every outgoing commit, and verifies that the proposed final commit's tree matches the clean workspace's tracked content. Git operations that use credentials operate only in the trusted checkout, with repository URL, target ref, hooks, and credential handling controlled by Omnigrex. Freeze the validated candidate before recording and pushing it, so later workspace changes cannot change what is published. Push that exact candidate SHA to only the scoped branch with the existing exact-head check and `--force-with-lease`; also require a fast-forward relationship to the old head. A clean workspace whose `HEAD` equals the expected head returns `changed: false` without pushing. A first publication with no new commits likewise creates no branch.

Publishing multiple commits exposes every intermediate commit's contents, even files removed later. This is inherent to Git history; final-tree checks must not be represented as a secret scan. Preserve agent-provided author/committer metadata as unverified text, while GitHub attributes the push to the Developer App. Preserve current Role permissions: the agent does not receive GitHub credentials and cannot select the push target.

## Durable preparation and recovery

The mutation reservation already stores the expected **old** head, operation identity, branch, and canonical request. Add a forward-only durable field for the validated **proposed** tip SHA, separate from `expected_sha`, and a format marker that distinguishes new reservations from pre-migration legacy rows even before a proposed tip has been recorded. Divide publication into preparation and push: inspect and freeze the trusted candidate, durably record its tip under the live Turn/mutation fence, and only then attempt the external push. Failure before recording cannot have pushed. Never infer an unrecorded proposed tip from a later workspace: a new Turn may have replaced that workspace.

For new-format operations, reconcile an uncertain push by fetching the scoped remote branch and verifying that the recorded proposed tip is the branch head or an ancestor of it, and that the persisted expected old head is the candidate's validated first-parent base. A later authorized publication may have advanced the branch without invalidating the earlier one. A remote head that lacks the candidate is not proof of success; retain the existing bounded unresolved-outcome recovery and eventual Human Handoff instead of automatically rebuilding and repushing missing Git objects. Concurrent or unexpected branch changes remain guarded by the lease and mutation fence. Successful publication returns the exact proposed SHA and continues to feed current Change Proposal and successor-Turn binding logic.

Retain legacy reconciliation only for pre-migration reservations: these identify the old orchestrator-authored commit through its operation trailer and single parent. A new-format reservation interrupted before tip recording must never fall back to trailer matching. Do not retroactively rewrite published heads. Persisted new-format evidence must survive process restart and workspace replacement. Repository metadata, credentials, file contents, and Git objects do not belong in the new database fields.

## Verification and rollout

Start with a failing Git fixture demonstrating that a locally committed merge is flattened by today's publisher. Then test multi-commit exact SHA preservation, multiple default-branch merges, legacy heads as publication bases, clean/no-op behavior, ignored and non-ignored files, staged and unresolved changes, first publication, rebase and non-default merge rejection, invalid objects and histories, historical `main` movement, lease races, credential isolation, and correct branch scope. Cover both new and legacy reconciliation, including a lost response after a successful push, later branch advancement, an absent candidate, restart/replacement of the agent workspace, and a pre-push failure after the tip was recorded. Exercise the durable schema and mutation fencing in focused database-backed tests. Run the focused suites, `mise run check`, and `mise run test-integration` as required by `AGENTS.md`; do not run destructive Compose tests unless their resource cleanup is authorized.

After the fix is deployed, use a new Developer Agent Turn to check out PR #16's current published head, merge and resolve the then-relevant `main`, commit, and publish through the fixed MCP tool. Verify the published merge's parents, exact remote head, and GitHub's eventually consistent mergeability separately. The new forward-only migration number must account for other work in flight: PR #16 currently contains an unmerged migration numbered `000028`, so its own migration may need renumbering when that Change Proposal next merges `main`. Link deployment or operational guidance to `docs/operator-guide.md`; do not alter the accepted `docs/plans/first-iteration.md` specification.
